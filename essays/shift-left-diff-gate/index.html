单人盯四端迭代时怎么防漏测：SpecGate 的规则设计与难例复盘

把提测前高频踩坑收敛成 11 条确定性规则后，我专门补了 6 个反例测试它的盲区——如实记录哪些修好了、哪些受限于正则仍会漏报或误报。

一、背景：等代码进了测试环境再点页面，排期根本不够用

单人负责 Android 学习平板端、双 Web 后台与服务端版本测试时，如果每次都等提测部署后再从头点一遍找低级漏洞，大量精力都会耗在返工打回上。早期试过把 git diff 直接喂给大模型审代码，但模型口径忽紧忽松，还经常编造不存在的代码行号。

二、SpecGate 的 11 条规则与补上的删除行检测

  • 先拆需求契约：从 PRD 梳理状态机流转、权限边界与禁用文案，附 SHA-256 摘要作为核对基准；工具本身不内置任何公司业务词。
  • 同时检查新增行与删除行：不仅拦新增 @SaIgnore、采信前端状态、无锁扣减、多行空 catch、mapper.updateById 丢弃返回值与平板离线进度覆盖，也拦删除 @PreAuthorize / @Transactional 这类高危改动，每条必带精确文件与行号。

三、补完 6 个难例后的真实成绩单

种子样例 4/4 通过只能证明规则能跑通；6 个难例里修好了删除权限注解、多行空 catch 和权限上移类级，但间接局部变量传参、只读 VO 减法误报和跨文件合并逻辑仍受限于单行正则——这些边界我都如实写在了仓库 README 里。
