为什么重型 Page-Object 框架两周就停摆，以及 TracePilot 的取舍

复盘从“搭一套规整的分层 UI 框架”到每天疲于修定位符，最终改成语义定位优先 + 后台被动接口检查的过程与已知局限。

一、踩坑：修定位符花的时间比手工测一遍还长

早期我尝试搭过标准的分层 Page-Object 前端自动化框架，但放进双周迭代里跑了不到两轮就维护不动了：登录页隐藏的原生复选框、div 写的伪按钮、window.open 弹出的新标签页报告，前端微调一次样式类名就成片报错。

二、更隐蔽的盲区：页面全绿，接口暗中泄密或假 200

单纯断言页面元素在不在，根本拦不住接口带病：曾遇到名册接口把整张表实体直接序列化返回，JSON 里顺手带出了学员 payPwd 密码哈希；还有看板接口超时仍返回 HTTP 200、只在包体写业务错误码，传统 UI 脚本一路绿灯漏了过去。

三、TracePilot 的务实做法与边界

  • 语义定位优先 + 组件兼容降级：用例只写可见文字，底层按「可访问性角色/标签 → 常见组件库兼容规则 → 精确文本」逐级降级，并把每步触发的策略记录在报告里。
  • 后台顺手检查全量接口与存储：流程运行时自动检查 JSON 响应和 localStorage，敏感字段和成功业务码支持在用例中配置，检查逻辑本身不依赖浏览器、可单独跑单元测试。
  • 已知局限：目前只在自建演示靶场上验证过，尚未在公开真实站点跑过并提交报告；敏感字段也只按键名识别，不识别值内容模式。
